# Pipeline (the six steps as jobs)

Scheduled work runs on Inngest. Every function declares `concurrency` and, where it calls a vendor, a `throttle`. Every LLM call uses `client.messages.parse` with `zodOutputFormat`; scheduled calls go through the Message Batches API with `custom_id = <jobType>:<entityId>:<schemaVersion>` and are idempotent on re-run. Model aliases: `MODEL_EXTRACT` (Haiku-class), `MODEL_MATRIX` (`claude-sonnet-5-5`), `MODEL_BRIEF` (`claude-opus-5-5`). Prompt and schema versions are stamped on every derived row.

## 1. Add query (interactive)

1. Normalise: NFKC, trim, collapse whitespace, lowercase, strip trailing punctuation. Reject operators (`site:`, `inurl:`, `intitle:`, `filetype:`, quotes, leading minus, `OR`), anything over 200 characters, and script/`hl` mismatches.
2. PII classifier: `MODEL_EXTRACT`, schema `{ is_person_query: boolean, reason: string }`, cached by normalised query. Person-name and private-individual queries are rejected with a reason.
3. Pre-check: DataForSEO Labs `related_keywords` for the query (about $0.01). Filter client-side for `serp_item_types` containing `ai_overview`; show "AI Overview seen on <last_updated_time>" and up to 5 sibling queries that trigger one.
4. Confirm: one DataForSEO Live Advanced call with `load_async_ai_overview=true` ($0.004). The result is stored as the series' first snapshot.
5. Join or create the `capture_series` for (normalised query, gl, hl, location_code, device, primary provider). Joining inherits the series' history. The `tracked_query` is `confirmed` if an AI Overview was present, else `watching` (captured daily, no LLM spend until one appears).

## 2. Schedule and capture (hourly cron, 15-minute jitter)

1. For every active series, compute today's slot plan from `cadence_max` (plus the second daily render while `week_one_until` is in the future) and the series timezone; `capture_day` is the local date.
2. For slots due this hour: check the org budgets of every subscriber and the global provider ceiling; insert `capture_attempt` with the idempotency key; submit up to 100 DataForSEO tasks per POST on the Standard queue with `load_async_ai_overview=true`, `device`, `os`, `location_code`, `language_code`, `tag` = idempotency key, `postback_url` with a secret.
3. Postback route: verify the secret, store the raw JSON in R2, emit one `capture/result.received` event.
4. Normalise: payload to `CanonicalSnapshot`; write `snapshot`, `aio_block`, `aio_reference`, `organic_result`, `snapshot_format`; compute `content_hash`; validate against the provider's JSON schema and count failures into provider health; drop images.
5. Sweeper (hourly): attempts with no postback after 20 minutes are polled with `task_get`; after 3 attempts the slot is `missed`. If provider health is under 0.8, the attempt fails over to SerpApi (`google` with `no_cache=true`, then `google_ai_overview` with the page token inside the same call within 60 seconds, counted as two searches). The idempotency key guarantees one snapshot and one cost row even if the primary later succeeds.
6. Canary series run on the same schedule at the product's expense and never enter LLM extraction.

## 3. Dedupe and extract (hourly batch assembler)

1. Exact `content_hash` match with any earlier render of the series: reuse that render's claims and formats; record the render; diff citations only.
2. Otherwise embed the markdown (voyage-4-lite) and compare with the previous render; cosine at or above 0.98 sets `near_dup_of`, reuses claims and diffs citations only.
3. Otherwise the snapshot joins one Message Batch on `MODEL_EXTRACT`. Input: the query, the AI Overview language, the blocks pre-split into sentences with `Intl.Segmenter`, each carrying its block id and inherited `reference_indexes`. The prompt follows the Claimify recipe: select verifiable sentences, disambiguate, decompose into self-contained atomic claims. Output schema (all fields required): `claims[] { sentence_ref, atomic_text, claim_type, reference_indexes[], entities[] { name, type, role, label } }`, `format_labels[]`, `answer_lead_sentence_ref`. Unknown `sentence_ref` or reference indexes fail validation; `refusal` and `max_tokens` stops retry once with a higher limit.
4. Embed claims and entity names. A claim joins the nearest cluster in the series at cosine at or above 0.90; pairs between 0.80 and 0.90 go to a batched `MODEL_EXTRACT` same-claim yes/no; otherwise a new cluster. Thresholds come from `analysis/thresholds.ts`, generated by the eval runner. Entities resolve through an alias table plus embeddings and are split into `recommended` and `cited_domain`; the self-promotional flag is set when a recommended entity's supporting references all resolve to its own registrable domain.
5. Free-tier orgs: no extraction before day 3 of their series subscription.

## 4. Count and diff (SQL, every capture day)

Recompute `series_metrics_daily` and `series_diff` per `metrics.md`. Render the daily digest per org (07:00 in the org's timezone) only for queries with a diff. Gate: `preliminary` at 3 capture-days; `seven_day` at 5 capture-days and 10 present renders.

## 5. Reverse-engineer (on the seven-day run)

1. Rank cited URLs by renders cited; exclude platform classes (reported separately as "not displaceable by a page"); take the top 10 (3 on free) plus any URL the user flags.
2. Fetch through the etiquette fetcher: named user agent, RFC 9309 robots (5xx is disallow, 24-hour cache), Content-Signal `ai-input=no` and aipref opt-outs honoured, at most 1 request per second per host with backoff on 429 and 403, DNS resolved once, private and metadata ranges denied, redirects re-validated up to 5 hops, 5 MB cap, text/html only. Firecrawl is the fallback when blocked or when under 200 words are extracted. Cached 7 days across all orgs in `cited_page`.
3. Compute features in code (Defuddle, Readability fallback under 200 words, cheerio): words and characters before the first direct answer (the LLM returns the sentence index; code computes the offset), heading outline, tables (rows by columns), lists, comparison blocks (two or more entities), numeric density, schema.org types, author, published and modified dates, word count, internal and external links, FAQ, page type.
4. One `MODEL_EXTRACT` batch call per page: `topics[]`, `entities[]`, `evidence_items[] { type: original_data | test_result | screenshot | quote | pricing | spec, excerpt <= 200 chars }`, `questions_answered[]`, `answer_sentence_index`, `approach_summary`. Markdown is truncated to 12K tokens by `count_tokens`. At most 5 quotes of at most 200 characters are kept; HTML goes to R2 for 14 days.
5. One `MODEL_MATRIX` batch call per run: topics by pages and entities by pages, each cell `covered | partial | missing` with an excerpt; `common_to_all_winners[]`, `gaps_no_winner_fills[]`, `aio_claims_unsupported[]` (clusters no cited page covers).

## 6. Brief (on the matrix)

One `MODEL_BRIEF` batch call (synchronous when triggered by an upgrade or a Playbook purchase). Input: the series aggregates, the coverage matrix, unsupported clusters, the format fingerprint, the customer's own-domain context. Output per `brief-schema.md`, with `evidence_refs` on every item and the AI-generated marker. Deterministic post-checks: every must-cover topic maps to a cluster with recurrence at or above 0.40; every must-mention entity recurs in at least 2 renders; no 12-word span of the brief matches a stored competitor quote. Regeneration is capped per plan; `cost_usd` comes from `usage`.

## 7. Publish and track

1. The customer submits own URL, brand terms and the published date. The deterministic draft score runs the page-feature extractor on the URL and compares it with the CORE pages' medians (topic coverage, entity coverage, format compliance, words to answer, numeric density, eligibility: indexable, no `nosnippet`, text in HTML). The same scorer accepts any pasted URL or text.
2. The own page is fetched, split by headings and embedded into `page_section`; refreshed weekly.
3. On every new snapshot: run the own-page matcher over references and brand terms over the text; map citing blocks to the best section at cosine at or above 0.8; write `citation_event` rows; email wins and losses with n and confidence once at least 3 renders of evidence exist; suppress losses inside a model-regime window.
4. Weekly `post_publish` runs recompute metrics in SQL; a brief v2 with a diff is offered at day 28 (counts against the regeneration cap).

## Cost and safety controls (apply everywhere)

- Per-org budgets (`captures_per_day`, `llm_usd_per_day`, `fetches_per_day`) checked before enqueue; global per-provider daily ceilings with auto-pause and one founder alert; Anthropic Console and Vercel spend limits.
- `usage_ledger` and `cost_rollup` written from vendor usage fields daily.
- One idempotency key per (series, capture_day, slot) across providers.
- Provider health computed from the last 50 attempts; automatic primary switch below 0.8 with a recovery window.
