# Completeness critique

A final reviewer read all seven dimensions and listed what was missing, what contradicted what, and what the plan must settle. Several of these became hard constraints in the plan (see `PLAN.md`). One critique item was later found to be wrong: Google did ship a Generative AI performance report in Search Console (UK subset 2026-06-03, worldwide 2026-08-31, impressions only); see the note in `00-summary.md`.

## Gaps

### No capture-pool architecture: every dimension assumes captures are per-organization (stack puts organization_id on every table incl. snapshots), but the capture unit is really (normalized query, gl, hl, location, device, provider, time-slot). Two customers tracking 'best crm' in en-US desktop should share one capture, and a new customer should inherit existing history for a query that is already in the pool.

**Why it matters.** It is the single biggest cost lever (SERP and per-snapshot LLM extraction both scale with unique captures, not with customers), it makes the free trial far cheaper to abuse, it fixes the 'no history on day 0' empty state for popular queries, and it is a schema decision that is painful to retrofit once snapshots carry organization_id.

**What to do.** Design decision, not research: model tracked_query (org-scoped, holds alias/notes/own-domain) -> capture_series (global, UNIQUE on normalized_query+gl+hl+location_code+device+provider) -> snapshot (global, keyed by series+captured_at). Org tenancy applies to tracked_query, analysis_run, brief and draft_score only; apply RLS there and not on the pool. Normalize queries before hashing (NFKC, trim, collapse whitespace, lowercase, strip trailing punctuation). Check DataForSEO retention and whether its task_get results can be re-read for 30 days (https://docs.dataforseo.com/v3/serp/google/organic/task_post/ says results are kept; Live results are not) so the pool can backfill from a missed postback.

### The unit economics are computed on different cadences in each dimension and the LLM extraction cost, not the SERP cost, is the real COGS driver. Verified 2026-10-06: DataForSEO Standard is $0.0006/SERP plus one base price for load_async_ai_overview (so $0.0012 per capture, refunded when asynchronous_ai_overview=false) at https://dataforseo.com/pricing/google-serp/google-organic-serp-api. With the pipeline dimension's $0.02-0.03 per-snapshot extraction estimate: 1 render/day desktop costs about $0.04 SERP + $0.40-0.75 LLM per query-month; 2 renders x 2 devices about $0.14 + $1.60-3.00; 3 renders x 2 devices (the aio-behaviour recommendation) about $0.22 + $2.40-4.50. GTM revenue per query is $2.60 (Starter $39/15), $1.98 (Pro $99/50), $1.25 (Agency $249/200).

**Why it matters.** At the aio-behaviour cadence the Pro and Agency tiers are loss-making before hosting, and even Starter is marginal; the GTM COGS guardrail only looked at SERP cost per check (it concluded captures must be under $0.01, which they are) and missed that each extra render triggers another LLM pass.

**What to do.** Before pricing is locked: (1) measure real per-snapshot token counts with count_tokens on 20 real AIO payloads (the claude-api skill confirms Haiku 4.5 $1/$5, Sonnet 5.5 $2/$10, Opus 5.5 $4/$20, batch 50% off, as of its 2026-09-25 table); (2) make renders/day and device variants explicit tier features (Starter: 1 render/day, 1 device; Pro: 3 renders/day, desktop+mobile; Agency: configurable) and expose them on the pricing page; (3) run per-snapshot extraction only on unique content: exact content_hash short-circuit plus near-duplicate detection (embedding cosine of the snapshot markdown >= 0.98 against the previous render of the same series reuses that render's claims and only diffs the citations); (4) build a COGS sheet with columns tier, queries, renders/day, devices, SERP $, LLM $, Inngest executions, and keep it in the repo as docs/unit-economics.md.

### The Search Console (step 6) integration is designed on a false premise. Verified 2026-10-06: Google's AI features page (https://developers.google.com/search/docs/appearance/ai-features, last updated 2025-12-10) says sites appearing in AI Overviews and AI Mode 'are included in the overall search traffic' and 'reported on in the Performance report, within the Web search type'; the Search Analytics API (https://developers.google.com/webmaster-tools/v1/searchanalytics/query) lists type values discover/googleNews/news/image/video/web and no AI value; the Performance report help page (https://support.google.com/webmasters/answer/7576553) contains no AI Overview or AI Mode breakout. Separately, Google OAuth: unverified apps are capped at '100 new users in total' (https://support.google.com/cloud/answer/7454865), sensitive-scope verification 'typically takes 3-5 business days' and requires a privacy policy on the same domain, a public homepage and a demo video (https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification); the classification of webmasters.readonly as sensitive vs restricted was not stated on either page.

**Why it matters.** The aio-behaviour dimension's 'new Generative AI performance report (impressions only)' cannot be relied on for the build plan; if it exists it is newer than every official page opened here. Building a GSC OAuth flow also front-loads Google verification work and a 100-user cap into v1.

**What to do.** Treat GSC as v1.1: ship render-based post-publish tracking first (URL cited / brand mentioned / survival rate). If GSC is kept, start the OAuth consent-screen verification in week 1 (privacy policy, homepage, demo video) and confirm the scope class on the Search Console API reference. Note the Performance report help page now lists 'Web: text-based' and 'Web: multimodal' search-type filters that the API page does not; verify whether that split exposes AI surfaces. Re-check with search whether Google announced a generative-AI report after 2025-12-10 (this pass had no search budget left).

### No specification for 'the user's page appeared' (own-page detection). Nothing defines URL normalization, canonical resolution, redirect following, subdomain/registrable-domain matching, or the difference between a cited URL, a cited domain and a brand mention; the thread's own screenshot shows chips like 'Tally Forms +1' (one chip, multiple references), so chip-level and reference-level matches also differ.

**Why it matters.** This is the step-6 'did it work' signal, the 'your domain appeared' email alert, the activation metric and the citation-win-rate KPI; without a deterministic matcher the product will produce false negatives (www vs non-www, trailing slash, utm, AMP, http->https redirects, m. subdomains, google.com/url?q= wrappers) and false positives (another path on a shared platform like medium.com or youtube.com).

**What to do.** Specify a url-match module with unit tests: normalize (lowercase host, strip scheme, default ports, fragments, trailing slash, utm_*/gclid/fbclid/ref params, index.html, percent-decode, punycode), unwrap google.com/url and AMP cache (cdn.ampproject.org) URLs, resolve up to 5 redirect hops and rel=canonical for both the cited URL and the user's URL (cache 7 days), registrable domain via the Public Suffix List (tldts npm), and emit match levels exact_url > canonical > path_prefix > subdomain > registrable_domain > brand_entity. Store provider 'source' names separately from domains (DataForSEO references carry source, domain, url, title, text per https://docs.dataforseo.com/v3/serp/google/organic/live/advanced/). Track competitor domains with the same module. For platform domains (youtube, reddit, medium, linkedin) require exact or path_prefix, never domain match.

### No AIO variant taxonomy or fixture corpus. The plan talks about 'AIO absent' but not: collapsed vs expanded ('Show more'), asynchronously loaded AIO, table elements, expanded elements with nested components, video elements, product/shopping grids, image-only chips, 'Dive deeper in AI Mode' hand-offs, provider_error, blocked/CAPTCHA, timeout, and the case where a query returns an AI Mode answer instead of an AIO. Verified 2026-10-06 on DataForSEO docs: ai_overview carries asynchronous_ai_overview, markdown, items[], references[]; item types include ai_overview_element (title, text, markdown, links, images, references), ai_overview_expanded_element (title, text, components[]), ai_overview_table_element (table_header/table_content, references) and ai_overview_video_element; and expand_ai_overview 'applies only to HTML task results'. SerpApi's page_token 'expires within 1 minute' (https://serpapi.com/google-ai-overview-api).

**Why it matters.** The normalizer, the diff engine and every frequency count depend on treating a collapsed render and an expanded render of the same AIO as the same answer with different visibility, not as two different answers; otherwise 'what keeps showing up' is contaminated by truncation. Claude Code cannot build or test the normalizer without fixtures.

**What to do.** Week-1 task: capture 30 buying-intent queries once each via DataForSEO Live Advanced JSON and HTML (expand_ai_overview=true) and via SerpApi, store the payloads under tests/fixtures/aio/<provider>/<variant>/, and answer empirically whether the DataForSEO JSON already contains the post-'Show more' text (compare JSON text length to the HTML). Define snapshot.status enum present_full | present_collapsed | absent | provider_error | blocked | timeout and snapshot.aio_kind enum text | list | table | product_grid | video | mixed. Keep AIO images out of storage (legal dimension).

### The 'day' is undefined. Captures are proposed at '06:00 and 18:00 local to the target market' (data acquisition) but scheduled by one Inngest cron at 03:00 UTC (stack); nothing defines capture_day from the location's timezone, how DST is handled, what happens when the DataForSEO Standard queue (documented '5 minutes on average') is slow or the postback never arrives, when a missed slot is retried, or how many days of 7 must exist before a report is generated (GTM's activation metric assumes >= 5 of 7).

**Why it matters.** Every recurrence metric (days_seen/total_days) and the 7-day trigger depend on a stable day boundary and on distinguishing 'no AIO' from 'capture missed'; without it the report fires with 4 snapshots or counts a late postback as the next day.

**What to do.** Design decision: per capture_series store timezone (derive from DataForSEO location via the serp/google/locations endpoint plus a tz lookup such as geo-tz, or let the user pick), compute capture_day in that tz, schedule per-series slots with an hourly Inngest cron that selects series whose local slot is due (jitter 15 min), use step.waitForEvent on the postback with a 20-minute timeout then fall back to task_get polling, mark the slot 'missed' after 3 attempts, and require n >= 5 capture-days and >= 10 renders before the 7-day report, n >= 3 days for a 'preliminary patterns' view.

### Query intake is unspecified: no normalization/dedupe rules, no maximum length, no handling of search operators (DataForSEO multiplies the price by 5 per operator such as site: or filetype:), no language/hl mismatch check, no ban on private-individual or PII queries (the legal AUP requires it), and the AIO-trigger pre-check is designed as a Live SERP call only.

**Why it matters.** Bad intake silently multiplies cost, breaks the capture pool's uniqueness key, and creates legal exposure; and the add-query screen is the first thing a trial user touches.

**What to do.** Verified 2026-10-06: DataForSEO Labs related_keywords ($0.0103 per request, depth 0-4, limit up to 1,000) and keyword_ideas return serp_info.serp_item_types whose possible values include ai_overview, plus last_updated_time and check_url (https://docs.dataforseo.com/v3/dataforseo_labs/google/related_keywords/live/, https://docs.dataforseo.com/v3/dataforseo_labs/google/keyword_ideas/live/); serp_item_types cannot be filtered server-side, so filter client-side. Use it as a one-cent pre-check and to suggest sibling queries that already trigger an AIO, then confirm with one Live Advanced call ($0.002 + $0.002 async) before the query is accepted. Reject operators, cap length at 200 chars, normalize as in the capture-pool gap, and run a cheap Haiku classifier for person-name/PII queries.

### Cost control and kill switches are absent from all seven dimensions: no per-org daily capture budget, no global provider spend ceiling, no circuit breaker when a provider is degraded (SerpApi's status page showed Google Search degradation Oct 1-6 per the legal dimension), no rule preventing double billing when a slow primary and the fallback both succeed, no Anthropic spend limit, and no budget for Inngest executions. Verified 2026-10-06: Inngest Free is 50k executions/month and 5 concurrent steps, Pro $99 for 1M executions and 100 concurrent steps, and 'an execution is metered per function run and per step' (https://www.inngest.com/pricing); at ~8-10 executions per capture the Free tier covers only ~5-6k captures/month, i.e. roughly 170-200 daily single-render series or ~30 series at 3 renders x 2 devices.

**Why it matters.** A stolen card, a runaway retry loop or a provider schema change can burn hundreds of dollars overnight on a solo-founder budget, and the stack dimension's 'Inngest Pro at ~100 customers' assumption breaks as soon as the multi-render cadence is adopted.

**What to do.** Implement: budget table per org (captures/day, LLM $/day) checked before enqueue; global daily ceilings per provider with automatic pause and founder alert; idempotency key per (series, slot) so fallback cannot run after the primary succeeded; Anthropic Console spend limit plus per-job max_tokens; Vercel Spend Management alerts; a daily cost roll-up job writing cost_usd per org. Decide Inngest Pro vs Vercel Workflows (no duration limits per https://vercel.com/docs/functions/configuring-functions/duration; Pro functions max 800s, 1800s beta) once renders/day is fixed.

### Abuse controls for the free hook are missing. The GTM dimension proposes email-only opt-in, one query tracked 7 days, a public shareable snapshot page and a blurred brief, but a free query costs roughly $0.50-1.00 in SERP + LLM over 7 days and the public page republishes Google's AIO text and citations at scale.

**Why it matters.** Disposable-email signups and bots can run up vendor spend with zero revenue, and public pages that reproduce AIO text wholesale look like exactly the 'raw SERP data redistribution' the legal dimension says never to offer.

**What to do.** Add Cloudflare Turnstile at signup, a disposable-email blocklist, one free series per verified email and per IP/day, device fingerprint limits, no LLM analysis for free accounts until day 3 (so abandoned trials cost only captures), cited-page fetching limited to 3 pages for free, API keys only on paid plans, and per-key rate limits. For the public page show citations and a short excerpt with the user's own commentary rather than the full AIO text, add noindex until counsel clears it, and verify SerpApi/DataForSEO terms on public redistribution (DataForSEO's terms as fetched do not restrict redistribution explicitly but §7.1 bars use that 'adversely affect[s] the business interests of the search engine providers'; https://dataforseo.com/terms-of-service, last updated 12 June 2026).

### The first seven days of a trial are not designed. Nothing specifies what the user sees on day 0 (today's AIO from the live check), days 1-6 (daily diff email, presence rate, 'preliminary patterns' with sample-size labels), day 7 (pattern report + brief preview), days 14-28 ('stable baseline'), or what happens when the AIO is absent on day 0 or disappears mid-week.

**Why it matters.** The brief is the aha moment but it arrives on day 7; trial-to-paid benchmarks (18% opt-in) assume users get value earlier, and an empty dashboard for six days is the most likely cause of churn.

**What to do.** Write the onboarding spec as UI states: 'confirmed AIO' vs 'no AIO yet, watching' (with sibling suggestions from DataForSEO Labs), progress meter 'n of 7 capture-days', daily email 'what changed' built from the diff engine, preliminary patterns unlocked at n >= 3 days with 'low confidence' badges, day-7 report, and a 'stability' badge at 14 days. Instrument activation as query confirmed -> 5 of 7 captures -> report opened -> brief generated, matching the GTM KPI.

### There is no Milestone 0 that validates the product before the SaaS is built: no concierge pilot, no provider side-by-side, and no demand test using the founder's existing Legiit audience.

**Why it matters.** The whole plan rests on three unproven assumptions: buying-intent queries trigger stable AIOs often enough, the LLM pattern report is good enough to act on, and customers will pay for the brief rather than the scrape. All three can be tested in two weeks for under $200 before any UI exists.

**What to do.** Milestone 0 (weeks 1-2): a TypeScript CLI that runs DataForSEO Standard + SerpApi for 50 real buying-intent queries, 3 renders/day, 7 days (about 50 x 3 x 7 x 2 providers x ~$0.0012-0.015 = under $40 on DataForSEO, SerpApi Production $150), stores raw payloads as fixtures, computes presence rate, citation Jaccard and cross-provider agreement, and produces 10 Markdown playbooks via Claude. Sell 10 playbooks manually as a Legiit gig at $99-149 and measure time-to-produce, willingness to pay and brief-to-build attach rate. Gate the SaaS build on >= 60% of queries having an AIO on >= 5 of 7 days and >= 5 paid playbooks.

### Step 6's 'which sections of my page got cited' has no mechanism. It needs the user's page URL, a passage-level matcher between each cited AIO block (text + reference_indexes) and the user's page headings/passages, and a definition of 'citation win' events (first_seen, lost, regained) at url, canonical, domain and brand-mention levels.

**Why it matters.** It is the retention loop (the thread's step 6) and the Agency tier's headline feature ('section-level which parts of my page got cited'), yet it is the least-specified feature in the plan.

**What to do.** Reuse the cited-page pipeline on the user's URL (re-fetch weekly), embed each heading-scoped passage, and when the user's URL is in a snapshot's references map each block that references it to the best-matching passage (cosine >= 0.8) to produce per-H2 citation counts over the rolling window; log win/loss events to drive emails. No external research needed; add it to the data model (page_section, section_citation).

### No system-owned canary set and no provider health scoring thresholds. Model-regime detection (aio-behaviour) and automatic failover (legal) both need a panel the product controls, independent of customer queries.

**Why it matters.** Without it a Google model change, a provider outage or a schema change looks like every customer's page failing at once, and failover triggers cannot be tuned.

**What to do.** Track 100 sentinel queries (mixed intent, 3 locales, both devices) at the product's expense; compute daily presence rate, sources-per-AIO and global citation Jaccard; alert on >2 sigma moves; score providers on success rate, latency, AIO presence vs sentinel baseline, and JSON-schema validation failures; switch primary automatically below a threshold and show a 'platform event' banner to users.

### Retention and storage policy is unresolved and object storage was never researched: the pipeline keeps raw_json forever and stores cited-page html; legal wants raw vendor JSON on a 90-day TTL, cited-page HTML discarded after 7-30 days and no full third-party text displayed; the stack dimension lists Vercel Blob vs R2 vs Supabase Storage as an open question.

**Why it matters.** Claude Code needs one policy to implement lifecycle rules, and egress pricing matters once raw HTML is stored per capture.

**What to do.** Adopt: raw provider JSON and HTML in object storage with a 90-day lifecycle rule, normalized snapshot rows forever, cited-page HTML 14 days, derived features and <= 5 quotes of <= 200 chars forever, AIO images never. Pick Cloudflare R2 for zero egress (verify current R2 pricing page before committing; not fetched in this pass) and store only pointers in Postgres.

### Locale handling stops at 'store gl + hl + location + device'. Missing: how the LLM prompts handle non-English AIOs, entity canonicalization across languages, which location granularity the product sells (country vs city), how a user picks a city (DataForSEO location_code lookup), how locale variants are priced, and that the brief's number/date/currency formats should follow the target market.

**Why it matters.** Agencies (the primary buyer) will immediately add UK/AU/CA and city-level queries; without a locale model the capture pool key, pricing and the LLM prompts all drift.

**What to do.** Define locale as {gl, hl, location_code, device} with a product rule 'one variant = one tracked query', seed a locations table from DataForSEO's serp/google/locations endpoint, pass the AIO language into every extraction prompt, and test claim clustering on 50 non-English snapshots before launch.

### No build sequencing, acceptance criteria, fixtures or eval harness exist for Claude Code to execute against. The seven dimensions give architecture and vendor choices, not milestones with definitions of done.

**Why it matters.** Claude Code works best from an ordered backlog with testable acceptance criteria; without one it will build UI before the capture layer is proven and will have nothing to test the analysis against.

**What to do.** Produce a milestone plan: M0 concierge CLI + fixtures (weeks 1-2); M1 capture pool, normalizer, status enum, storage, diff (weeks 2-4) with golden tests on the fixture corpus; M2 claim extraction, clustering, frequency SQL, 7-day report (weeks 4-5) with a 200-pair labelled claim-similarity eval (use the claude-api skill's build-eval flow); M3 cited-page pipeline, coverage matrix, brief (weeks 5-7); M4 auth, billing, onboarding states, abuse controls, cost guards (weeks 7-8); M5 post-publish tracking, section matcher, emails (weeks 8-9); M6 API/MCP on derived data, agency workspaces (later). Pin versions on day 0 and avoid any framework released the same day (the stack dimension cites Next.js 16.4 and SvelteKit 3.0.1 as released 2026-10-06; re-verify before pinning).

## Contradictions between dimensions

- Search Console: aio-behaviour says a 'new Generative AI performance report' exists (impressions only) and legal says to present GSC as 'Web search performance including AI features' because Google does not break out AIO impressions. Verified 2026-10-06 on Google's own page (https://developers.google.com/search/docs/appearance/ai-features, last updated 2025-12-10): AI Overviews and AI Mode are 'reported on in the Performance report, within the Web search type'; the Search Analytics API lists no AI search type or value. The legal dimension is right unless Google shipped something after Dec 2025; aio-behaviour's claim (and its cited 'last updated 2026-07-10' page) must be re-checked.
- Capture cadence: data acquisition recommends 2 samples/day x desktop+mobile; aio-behaviour recommends >= 3 renders/day and cites 7-8 renders/day as the statistically sound figure; analysis-pipeline costs the LLM step at one snapshot per query per day; GTM prices Starter on 'daily AIO snapshots'. These are incompatible without a dedupe rule and per-tier cadence; at 3 x 2 renders the LLM extraction alone exceeds Pro/Agency revenue per query.
- Raw data retention: analysis-pipeline says 'keep raw_json forever'; legal says store raw vendor JSON 'immutable, 90-day TTL'. Cited pages: pipeline stores html in cited_page; legal says discard raw HTML after 7-30 days and never display full third-party text.
- Stability tiers: aio-behaviour uses CORE >= 80% / RECURRING 40-80% / ROTATING < 40% of renders; analysis-pipeline uses core >= 85% / rotating 40-85% / volatile < 40% of days. Different thresholds, different names, and different denominators (renders vs days).
- AIO intent mix: GTM states AIOs are '76-80% informational and under 3% transactional' (Semrush) while aio-behaviour and data acquisition cite Semrush's later panel at 57.1% informational, 18.6% commercial, 13.9% transactional. Same vendor, different study dates; the onboarding copy and the trigger-rate warning must use one figure.
- API/MCP: competitors recommends a documented REST API and MCP server from day one; legal says never offer raw SERP data export or an API that resells vendor payloads. Resolvable only if the API exposes derived data (claims, frequencies, matrices, briefs) and not AIO text or reference lists verbatim; the plan must say so explicitly.
- Product name: GTM proposes 'Legiit Overviews'; legal says avoid 'Google', 'AIO', 'AI Overview(s)', 'Gemini', 'SGE' in the name. Verified 2026-10-06 that Google's trademark list (https://about.google/brand-resource-center/trademark-list/) includes 'SGE', 'Gemini' and 'Google Search' but not 'AI Overviews' or 'AI Mode'; 'Overviews' alone is likely defensible but should go to counsel.
- Scheduling: data acquisition wants captures at 06:00 and 18:00 local to the target market; stack designs a single Inngest cron at 03:00 UTC with 5-minute jitter.
- Primary provider: data acquisition makes DataForSEO primary; legal flags DataForSEO ToS §7.1 (verified text: SERP data 'shall not be used to compete with or adversely affect the business interests of the search engine providers', with §7.2 indemnity, last updated 12 June 2026) and notes only SerpApi/SearchApi carry a legal shield (verified: SerpApi Legal Shield from the $150/mo Production plan, up to $2M). The plan should name DataForSEO primary for cost only after written confirmation from DataForSEO.
- Jake Ward's relationship to Mentions.so: GTM leaves it open and plans to tag his thread and position the product as an upsell to his audience; competitors notes he lists Mentions.so on jakeward.io. Verified 2026-10-06: jakeward.io lists 'Mentions for AI visibility insights' under 'How I can help you', i.e. he markets it as his own offering. He should be treated as a competitor's distribution, not a neutral evangelist.
- SerpApi double billing: data acquisition says SerpApi states in writing that the page_token path 'will count as two SerpApi searches'; the SerpApi Google AI Overview API page and pricing page fetched on 2026-10-06 do not contain that statement (pricing says only successful searches count). The claim may live on another docs page; confirm before budgeting 2 credits per capture.
- Haiku 4.5 as the cheap extraction tier (analysis-pipeline) vs Anthropic's deprecation page (verified 2026-10-06): claude-haiku-4-5-20251001 is Active with tentative retirement 'Not sooner than October 15, 2026' and Sonnet 4.5 was deprecated on September 30, 2026; the pipeline already flags this but the model IDs in the plan must be aliases, not hard-coded.

## Strongest recommendations

- Add Milestone 0 before any SaaS code: a TypeScript CLI pilot (DataForSEO Standard + SerpApi, 50 buying-intent queries, 3 renders/day, 7 days) that produces fixture payloads and 10 Claude-generated playbooks sold manually through Legiit; gate the build on AIO presence >= 5 of 7 days for >= 60% of queries and >= 5 paid playbooks.
- Re-architect capture as a global pool keyed on (normalized query, gl, hl, location_code, device, provider) with per-org subscriptions; tenancy and RLS apply to tracked_query, analysis_run, brief and draft_score, not to snapshots. This cuts SERP and LLM cost per customer, gives instant history for shared queries, and makes free-trial abuse cheaper to absorb.
- Fix one cadence per tier and make LLM extraction content-deduplicated: Starter 1 render/day desktop, Pro 3 renders/day desktop+mobile, Agency configurable; extract claims only for unique content (hash plus near-duplicate embedding check) so extra renders cost SERP money only. Publish the COGS table in the repo and re-run it after measuring real token counts.
- Define snapshot.status (present_full | present_collapsed | absent | provider_error | blocked | timeout) and a variant taxonomy, and build the normalizer against a fixture corpus captured in JSON and HTML from DataForSEO and SerpApi in week 1; verify empirically whether DataForSEO JSON includes post-'Show more' text since expand_ai_overview 'applies only to HTML task results'.
- Specify the own-page matcher as a standalone module with tests (normalization, redirect and canonical resolution, PSL registrable domain, match levels exact_url > canonical > path_prefix > subdomain > registrable_domain > brand_entity) and use it for competitor domains too; this module feeds the alert emails, the activation metric and the citation-win KPI.
- Defer the Search Console integration to v1.1 and make render-based tracking the primary step-6 signal; if GSC is kept, start Google OAuth verification (privacy policy, homepage, demo video; 100-user cap until verified) in week 1.
- Use DataForSEO Labs related_keywords ($0.0103/request, serp_item_types can include ai_overview, with last_updated_time) as the one-cent AIO-trigger pre-check and sibling-query suggester at add-time, confirmed by a single Live Advanced call before the query is accepted; reject search operators (price x5 each) and PII queries.
- Put cost and abuse guardrails in the first sprint: per-org capture and LLM budgets, global provider ceilings with auto-pause, idempotent (series, slot) keys so fallback cannot double-bill, Turnstile plus disposable-email blocking, one free series per verified email, no LLM analysis for free accounts before day 3, and Anthropic/Vercel spend limits.
- Scope any public API/MCP and the public share pages to derived data (claims, frequencies, coverage matrices, briefs, short excerpts) and never to raw AIO text or reference lists; keep SerpApi Production ($150/mo, Legal Shield) in the stack and obtain written confirmation from DataForSEO on ToS §7.1 before relying on it as primary.
- Hand Claude Code an ordered milestone backlog with acceptance criteria, the fixture corpus, a labelled 200-pair claim-similarity eval set, pinned versions (avoid same-day releases), and a single data-retention policy (raw payloads 90 days, cited-page HTML 14 days, normalized data forever, no AIO images).

## Risks for the plan

- COGS inversion: the plan prices on SERP cost ($0.0012/capture) while per-snapshot LLM extraction ($0.02-0.03 estimated, unmeasured) dominates; at the multi-render cadence Pro ($1.98/query) and Agency ($1.25/query) lose money unless extraction is deduplicated and batched.
- Legal supply-chain risk remains live: Google v. SerpApi (amended complaint Aug 2026) and DataForSEO ToS §7.1 both touch this exact use; Google's Terms (effective July 30, 2026, verified) bar automated access 'in violation of the machine-readable instructions' and google.com/robots.txt disallows /search (verified), and the same Terms bar 'using AI-generated content from our services to develop machine learning models', so no fine-tuning or distillation on AIO corpora, ever.
- Public shareable snapshot pages and a day-one API could be characterised as redistributing SERP data at scale, undermining the 'analysis tool, not data API' posture the legal dimension relies on.
